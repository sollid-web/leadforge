## Operational configuration seen in code

App env names include Supabase URL/publishable key, server-only `SUPABASE_SERVICE_ROLE_KEY`, `OWNER_DATA_ENCRYPTION_KEY`, `NEXT_PUBLIC_APP_URL`, optional `CRON_SECRET`, `RENTCAST_API_KEY`, Untera key/authorization flags, Resend settings, Stripe settings, and optional scraper worker URL/token. These are examples/placeholders, not proof of configured runtime values. For safe simulation, external-send/payment/provider/worker secrets should remain absent unless a dedicated test environment is selected.

## Integration blockers carried into Autopilot work

- The batch offers UI depends on `GET /api/lead-batches`; it selected `price_cents` while the migration defines `price_minor_units`/`unit_price_minor_units`. This has been corrected locally to `price_minor_units`; the end-to-end batch path still needs staging verification.
- Cross-tenant checks on the legacy interest/match RLS path require hardening and two-organization verification before granting broader autonomous access.
- Unknown-permission contact policy and `paid` versus `delivered` buyer release semantics require explicit decisions and server-side enforcement.
- n8n and worker runtime health, retries, idempotency, secrets, and monitoring are not configured by this repository alone.

## Autopilot implementation boundary

This inventory is not evidence that the integrations are live. A future implementation can add disabled n8n workflow exports and authenticated, idempotent application orchestration contracts, but activation requires an administrator-owned n8n instance and test credentials. Real collection, emails, and payment processing must remain off until their provider permissions, test-mode credentials, staging project, and activation controls are verified.
